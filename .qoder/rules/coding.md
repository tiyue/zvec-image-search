## Coding 规范

### 实现前

- 不要假设，不要掩盖困惑。
- 明确说明假设、取舍和成功标准。
- 存在多种理解时，列出差异并澄清。
- 有更简单的方案时直接说明。
- 需求有风险时直接指出。
- 不清楚的地方先提问。
- **明文写出本次修改相关的文件位置范围，并再三强调不得修改无关部分。**

### 实现中

- 用能解决问题的最少代码。
- 不添加用户没要求的功能、配置项、抽象或错误处理。
- 不写猜测性代码。
- 只改必须改的地方，只清理自己制造的问题。
- 不顺手改进旁边的代码、注释或格式。
- 匹配现有代码风格。
- 发现无关死代码时只提出，不删除。
- 每一行改动都应能追溯到用户请求。

### 验证

- 修 bug 时先复现问题，再验证修复。
- 添加校验时补充非法输入测试。
- 重构时确认重构前后行为一致。
- 多步骤任务需要给出简短计划和验证项。
- 不交付假想、占位、未验证的结果，要求开发功能不要交付 demo。
**- 自己至少做一次冒烟测试再交付，哪怕是代码级别的。**

### 解耦

按照业务功能模块划分代码。模块应有清晰职责和接口，减少耦合。可以拆成几个模块组合时优先拆分，但不要为了单一职责做过度原子化拆分。

## UI 设计

> 任何前端或者客户端 Coding 工作都视为 UI 设计

- Web 设计必须响应式适配移动端，优先使用 flex 或 grid。
- 不要把浅底深描边作为主要视觉风格，除非符合现有设计系统。
- 禁止过大的 title、按钮、图表和其他 UI 元素，信息密度应保持合理。
- CRUD 表单等复杂输入应放在二级页面或模态中，一级页面只暴露入口。
- 禁止把蓝紫渐变作为按钮、标签、卡片等视觉重点。
- 禁止卡片套卡片。卡片内部聚合信息时使用分割线、间距和排版。
- 所有设计元素都必须有明确功能目的，不能纯装饰。
- 禁止使用颜色点作为状态表示，除非用户明确需要。
- 使用语义化 HTML，例如 `<button>`、`<nav>`、`<header>`。
- 新项目必须先定义 CSS 变量，包括颜色、字体、字号、圆角、间距等基础 token。
- 使用 8pt 网格系统，必要时兼容 4pt 和 12pt。
- 文本必须有足够对比度。
- 同一行或同一列内的元素必须对齐。
- UI 文本必须简洁，并遵守“最终产物文案”规则。
- 设计必须包含 light mode 和 dark mode，并支持跟随系统。
- 所有设计交付前必须通过 computer user 或者浏览器截图或进行视觉检查。
- 使用 Figma 进行设计时（$figma-use 等和 figma 相关的工具），如无必要，则必须使用 auto layout，同时内容元素如果不是需要特定尺寸（如 icon 等），其尺寸必须使用 fill 或者 hug，这很重要！
- 弹出式菜单项必须有「点击其他地方收起菜单」功能


## 普通设计

- 如果没有特殊说明，所有图片生成类需求默认使 $image-gen，而不是 SVG 或者 HTML 排版！

## 收尾工作

### Spec 更新

如果是开发项目，请查看是否有 Spec 文档；没有的话，请创建 `./docs/spec.md`（小项目）、`./docs/spec/xx.md`（大项目）。
如果已经存在 spec，则直接编辑 spec 文档。
将本次改动更新到 spec 文档中，并做好 spec 文档在项目 AGENTS.md 中索引维护

## 版本管理

- 任何一次任务结束之后，请检查一下同项目有没有其他的 Codex Session 正在进行，如果有，则直接结束；如果没有，则提交一次 git commit
- 如果进行了一个较大的功能更新，提醒我是否需要 git push （如果设置了 git remote）
