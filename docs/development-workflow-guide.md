# 从想法到稳定发布：软件开发全流程学习与实践手册

- 状态：长期维护
- 适用对象：非技术产品负责人、独立开发者，以及使用 Codex 协作开发的人
- 适用项目：Zvec / 曜镜（YaoLens），也可迁移到其他软件项目

## 1. 先回答你的核心困惑

正常的软件开发并不是“第一次就把所有事情想完整，然后一次写完”。任何真实产品都会迭代。专业流程真正解决的是：

1. 把最便宜的修改放在需求和原型阶段完成。
2. 把必须决定、可以延后、目前未知的事项明确分开。
3. 开发前定义什么叫完成，避免写完之后才讨论标准。
4. 每次变更都先评估影响，再决定是否进入当前版本。
5. 用文档、测试和发布记录保存已经确认的结论，避免反复遗忘。

因此，问题不在于“改了很多次”，而在于这些修改属于哪一类：

| 类型 | 是否正常 | 例子 |
| --- | --- | --- |
| 探索性迭代 | 正常 | 看过低保真原型后，发现按钮位置不顺手 |
| 新需求变化 | 正常，但要走变更流程 | 开发中临时增加批量删除 |
| 约束遗漏返工 | 应尽量减少 | 写完才发现还要支持暗色、窄窗、取消和异常状态 |
| 已确认内容回退 | 流程缺陷 | 修复预览后又让图片重新闪烁 |
| 无证据的猜测实现 | 应禁止 | 没有真实相机参考图却模拟创意外观色彩 |

专业开发也无法在立项时知道全部细节。更现实的目标是：

- 高风险、难回滚、影响架构的未知项必须在开发前暴露。
- 低风险、容易调整的细节可以在开发中逐步确认。
- 所有未知项必须明文记录，不能由开发者或 AI 猜测。

一句话概括：**允许迭代，但不允许没有边界、没有记录、没有验收标准的迭代。**

## 2. 你在开发中的角色

即使项目主要由你和 Codex 完成，仍然需要区分几种职责。一个人可以兼任多个角色，但不能省略相应的思考。

| 角色 | 主要责任 | 需要回答的问题 |
| --- | --- | --- |
| 产品负责人 | 决定为什么做、给谁做、先做什么 | 用户价值是什么？哪些内容不做？ |
| 交互/视觉设计 | 定义用户怎样完成任务 | 页面、状态、反馈和异常怎样表现？ |
| 技术负责人 | 决定怎样安全实现 | 模块边界、数据、性能和兼容方案是什么？ |
| 开发者 | 按确认内容实现 | 每一行改动对应哪条需求？ |
| 测试/验收者 | 独立证明结果符合要求 | 怎样复现、怎样判定通过或失败？ |
| 发布负责人 | 控制版本和上线风险 | 构建、回滚、下载、监控是否准备好？ |

在个人项目中，最容易出现的问题是同一时刻同时扮演所有角色：一边写代码，一边改变需求，一边凭感觉验收。解决办法不是增加会议，而是按阶段切换角色。

## 3. 一套完整但不过度繁琐的开发流程

### 3.1 全流程总览

| 阶段 | 核心问题 | 主要产物 | 进入下一阶段的条件 |
| --- | --- | --- | --- |
| 0. 需求入口 | 发生了什么，为什么现在要处理？ | 需求卡或缺陷卡 | 问题可以复述和复现 |
| 1. 立项 | 值不值得做，边界是什么？ | 一页立项说明 | 目标、非目标、风险已确认 |
| 2. 调研与可行性 | 是否存在技术或业务未知？ | 调研结论、技术试验 | 高风险未知已验证或明确阻塞 |
| 3. 需求定义 | 软件必须做什么？ | PRD、验收标准、约束清单 | 达到需求就绪标准 |
| 4. 原型与交互 | 用户具体怎样操作？ | 原型、状态图、视觉规则 | 原型冻结并签字确认 |
| 5. 技术设计 | 怎样实现且不破坏现有功能？ | 技术方案、接口、数据设计 | 方案可实现、可测试、可回滚 |
| 6. 计划与拆分 | 以什么顺序交付？ | 里程碑、任务、测试计划 | 每个任务大小可控 |
| 7. 开发 | 按边界实现 | 代码、测试、迁移、文档 | 达到完成定义 |
| 8. 测试 | 是否满足功能和质量要求？ | 测试报告、缺陷清单 | 发布阻塞缺陷清零 |
| 9. 用户验收 | 是否真正解决用户问题？ | UAT 结果、验收记录 | 产品负责人明确接受 |
| 10. 发布 | 怎样安全交付？ | 安装包、校验和、发布说明 | 发布门禁全部通过 |
| 11. 监控与复盘 | 上线后是否稳定，学到了什么？ | 指标、事故记录、改进项 | 改进项进入后续计划 |
| 12. 维护与退役 | 怎样升级、迁移或下线？ | 兼容策略、迁移和退役计划 | 用户数据和依赖已妥善处理 |

这里的“冻结”不是永远不能改，而是表示：继续修改必须先说明原因和影响，不能悄悄改变。

### 3.2 五道最重要的确认关

小团队不需要复杂审批，但至少保留以下五道关：

1. **立项确认**：目标和范围值得投入。
2. **需求就绪**：约束、异常和验收标准足够开发。
3. **原型冻结**：用户流程、页面状态和主要文案已确认。
4. **开发完成**：代码、测试和文档满足完成定义。
5. **发布就绪**：产物、回滚、验证和发布说明全部通过。

任何一道关没有通过，都不应该用“先写出来再说”掩盖未知。可以做技术试验，但技术试验不能冒充正式功能。

## 4. 阶段 0：正确记录一个需求或缺陷

### 4.1 新需求至少要包含什么

- 谁会使用。
- 用户当前在做什么。
- 当前痛点是什么。
- 希望出现什么结果。
- 为什么现在要做。
- 有什么已知限制。
- 怎样判断它有价值。

不够清楚的表达：

> 增加封面功能。

可开发的表达：

> 在 ARW 选片项目列表中显示封面，帮助用户快速识别拍摄批次。默认封面取该项目按确定顺序排列的第一张有效图片缩略图。封面必须持久化；源文件丢失时显示明确占位，不得反复闪烁。

第二种表达仍有问题需要确认，例如“确定顺序”是什么，但未知已经暴露出来了。

### 4.2 缺陷至少要包含什么

- 运行版本、系统和设备。
- 前置条件。
- 可重复的操作步骤。
- 实际结果。
- 期望结果。
- 出现频率。
- 截图、视频、日志或样本文件。
- 是否导致数据损坏或核心流程无法使用。
- 最近一次正常的版本。

缺陷修复必须先复现。无法复现时，应先增加证据或最小诊断，而不是直接猜测修复。

## 5. 阶段 1：立项

### 5.1 立项不是写长报告

立项的目标是决定“做不做”和“做到哪里”，通常一页即可。

必须明确：

- **背景**：当前问题和用户场景。
- **目标**：本次完成后带来的变化。
- **非目标**：本次明确不解决什么。
- **用户**：主要用户、次要用户、暂不支持的用户。
- **成功指标**：功能结果、质量结果、业务结果。
- **时间和资源**：预计周期、可用人员、设备和数据。
- **硬约束**：平台、兼容、法律、隐私、发布矩阵。
- **主要风险**：最可能导致延期、返工或失败的事项。
- **停止条件**：什么时候应暂停或取消项目。

### 5.2 目标要描述结果，不要只描述功能

较弱的目标：

> 做一个 ARW 页面。

较好的目标：

> 摄影用户在不修改原始 ARW 文件的前提下，可以导入 Sony A7M4 拍摄批次，在首次可见时间达到约定门槛后完成浏览、评级、对比和导出，并且连续切图不闪烁。

### 5.3 使用“目标 / 非目标”控制范围

例如：

**目标**

- 导入 A7M4 ARW、JPG、PNG。
- 快速选片、评级、色标、对比、导出。
- 保留源文件，不参与主图库搜索。

**非目标**

- 不做完整 RAW 编辑器。
- 不承诺 Sony 创意外观的像素级复刻。
- 不支持未验证相机型号。
- 不改 Android 和推荐系统。

非目标不是以后永远不做，而是保护当前版本。

## 6. 阶段 2：调研、技术预研和风险验证

### 6.1 什么情况必须先调研

- 依赖真实硬件、私有格式或外部服务。
- 性能目标没有数据支撑。
- 第三方库是否支持目标平台不确定。
- 方案可能改变数据库、文件或发布矩阵。
- 功能涉及不可逆删除、隐私、安全或付费。
- 视觉结果需要真实参考数据校准。

### 6.2 技术试验和正式功能的区别

技术试验只回答一个问题，例如：

- rawpy 能否稳定解码 A7M4 各种 RAW 模式？
- 1000 张图片时首屏延迟是多少？
- 内嵌 JPEG 是否带有正确方向信息？

技术试验应有：

- 明确假设。
- 固定样本和环境。
- 可重复步骤。
- 通过门槛。
- 结论和限制。

如果样本不足，就只能写“非正式结果”，不能宣称正式验收通过。

### 6.3 未知项处理方法

每个未知项只能进入以下状态之一：

| 状态 | 含义 | 下一步 |
| --- | --- | --- |
| 已确认 | 有明确事实或决策 | 写入权威文档 |
| 待调研 | 可以通过试验获得答案 | 建立预研任务 |
| 待用户决定 | 属于产品取舍 | 提供选项和影响 |
| 外部阻塞 | 需要设备、数据或授权 | 明确阻塞条件 |
| 当前不做 | 风险或价值不合适 | 写入非目标 |

禁止把“待确认”直接翻译成代码。

## 7. 阶段 3：把需求写到可以验收

### 7.1 需求文档不只是功能列表

一份可开发的需求通常包含：

1. 背景与目标。
2. 范围与非范围。
3. 用户、角色和权限。
4. 核心流程。
5. 功能需求。
6. 数据与业务规则。
7. 页面和交互状态。
8. 异常与边界情况。
9. 非功能要求。
10. 验收标准。
11. 依赖、风险和未知。
12. 版本、状态和决策记录。

### 7.2 约束完整性检查表

这是减少返工最关键的一部分。每个功能都应检查以下类别，不适用时也应写“不适用”。

#### 用户与权限

- 谁能看到、使用、修改和删除？
- 匿名、普通用户、管理员有什么差异？
- 多用户或多会话怎样隔离？

#### 输入

- 支持哪些格式、尺寸、编码、数量和路径？
- 最大值、最小值、空值和重复值怎样处理？
- 输入无效时阻止、跳过还是自动修复？

#### 输出

- 输出内容、格式、命名、排序和保存位置是什么？
- 成功后给用户什么反馈？
- 部分成功如何表达？

#### 数据与持久化

- 数据存在哪里，何时写入？
- 冷启动后是否保留？
- 源数据变化后怎样失效和刷新？
- 旧版本数据怎样迁移？
- 删除时是软删除、暂存还是永久删除？

#### 顺序与唯一性

- “第一张”“最新”“默认”分别按什么字段判断？
- 相同时间或相同名称怎样稳定排序？
- 去重依据是什么？

#### 状态

- 初始、空、加载、成功、失败、取消、离线分别是什么样？
- 是否允许重试？
- 切换页面、后台恢复、冷启动后状态怎样变化？

#### 并发与重复操作

- 连续点击是否去重？
- 同一任务能否并发执行？
- 取消发生在最后一步时怎样定义？
- 请求重复到达是否产生重复数据？

#### 错误与恢复

- 哪些错误用户可以自行处理？
- 哪些错误需要日志或人工处理？
- 失败后保留旧内容、回滚还是显示空白？
- 中途失败是否留下临时文件或半成品？

#### UI 与交互

- 桌面、窄窗、移动端分别怎样布局？
- light、dark、系统缩放和高 DPI 是否支持？
- 键盘、鼠标、触屏和无障碍需求是什么？
- 菜单如何打开、关闭、按 Escape 退出？
- 文案、禁用态、危险操作确认是什么？

#### 性能

- 数据规模是什么？
- 冷启动、热启动、首屏、切换和批处理的目标是多少？
- 使用 P50、P95 还是最大值？
- 测试硬件、样本和依赖版本是什么？

#### 兼容

- 操作系统、CPU、浏览器、Android API 和 Python 版本是什么？
- 旧项目、旧数据库和旧缓存怎样处理？
- 第三方依赖升级的边界是什么？

#### 安全与隐私

- 是否上传用户数据？
- 是否记录路径、图片内容或个人信息？
- 令牌怎样存储和传输？
- 是否防止目录穿越、越权和危险文件操作？

#### 可观察性

- 哪些操作必须记录日志？
- 需要哪些指标、错误码和任务进度？
- 出现问题时怎样定位到版本、输入和执行阶段？

#### 发布与回滚

- 哪些平台需要产物？
- 是否需要签名、校验和和验证报告？
- 失败时怎样回到上一个版本？
- 新旧数据能否兼容回滚？

### 7.3 用场景描述代替模糊形容词

“快速”“稳定”“友好”不能直接测试。应改成可观察结果。

示例：

> 给定一个包含 1000 个成员、至少 300 个有效 A7M4 ARW 的固定项目；当用户在约定测试机上冷启动并打开项目时；首批 24 张可操作缩略图的 P95 不超过约定数值，且连续切换 100 张时已显示的最佳预览不得降级为低清预览。

常用格式：

- **Given**：已知什么前置条件。
- **When**：用户执行什么操作。
- **Then**：软件必须出现什么可观察结果。

### 7.4 给需求编号

编号让代码、测试和问题都能追溯。

示例：

- RAW-COVER-001：默认封面来源。
- RAW-COVER-002：首图删除后的回退。
- RAW-PREVIEW-003：预览阶段只升不降。
- RAW-LOOK-004：未校准外观必须禁用。

测试报告可以直接写“验证 RAW-PREVIEW-003”，减少歧义。

### 7.5 使用优先级保护版本

推荐使用：

- **Must**：本版本缺少就不能发布。
- **Should**：重要，但必要时可延后。
- **Could**：有余量才做。
- **Won't now**：明确不进入本版本。

不要把所有事项都标成 Must。否则优先级等于不存在。

## 8. 阶段 4：原型和交互确认

### 8.1 为什么原型能大幅减少返工

代码是昂贵的表达方式。原型可以在没有数据库、接口和迁移成本时暴露：

- 页面层级是否正确。
- 功能是否太拥挤。
- 用户是否找得到入口。
- 操作顺序是否自然。
- 状态和反馈是否缺失。
- 文案是否能理解。

### 8.2 原型的三个层级

| 层级 | 用途 | 不应该讨论什么 |
| --- | --- | --- |
| 流程图 | 确认入口、步骤和分支 | 颜色、阴影、精确尺寸 |
| 低保真线框 | 确认布局、信息层级和操作 | 最终视觉细节 |
| 高保真原型 | 确认组件、间距、文案和响应式 | 后端是否已完成 |

不要一开始就做高保真。流程错了，漂亮的界面也要重做。

### 8.3 原型必须覆盖的状态

至少检查：

- 首次进入。
- 有数据。
- 空数据。
- 正在加载。
- 加载较慢。
- 请求失败。
- 部分成功。
- 禁用。
- 危险操作确认。
- 取消和重试。
- 数据过多。
- 超长文件名和极端尺寸。
- 窄窗、移动端。
- light 和 dark。
- 键盘焦点和菜单收起。

只画“理想成功页面”通常会把大量决策推迟到开发阶段。

### 8.4 原型冻结记录

冻结时记录：

- 原型版本和日期。
- 已确认页面和状态。
- 尚未解决的问题。
- 不进入本版本的内容。
- 允许开发者自行决定的细节。
- 必须再次询问用户的事项。

冻结后仍可变更，但需创建变更记录。

## 9. 阶段 5：技术设计

技术设计不是为了炫耀架构，而是提前回答那些写到一半才会变贵的问题。

### 9.1 技术方案至少包含

- 现状和已有模块。
- 修改文件或目录范围。
- 明确不得修改的部分。
- 模块职责和调用关系。
- API 请求、返回、错误码和版本。
- 数据表、字段、索引和迁移。
- 缓存、失效和源版本规则。
- 并发、取消、重试和幂等。
- 性能预算和数据规模。
- 安全与危险操作。
- 兼容和回滚。
- 测试策略。
- 日志和监控。
- 备选方案与取舍。

### 9.2 优先使用垂直切片

垂直切片是一个从界面到数据再到测试都能工作的最小完整流程。

例如 ARW 模块可以按以下顺序交付：

1. 创建项目并导入一个小目录。
2. 展示稳定缩略图。
3. 打开单图预览。
4. 评级并持久化。
5. 筛选和排序。
6. 对比。
7. 导出。
8. 删除和恢复边界。

不建议先把全部后端写完，再一次连接全部前端。那样风险会集中到最后。

### 9.3 记录技术决策

重要决策应写成简短 ADR：

- 决策标题。
- 背景。
- 候选方案。
- 最终选择。
- 原因和代价。
- 以后什么条件下重新评估。

例如：

> 决定：ARW 创意外观在没有可信 A7M4 参考样本前只允许 As Shot。
>
> 原因：猜测参数会给用户错误的色彩预期。
>
> 代价：第一版功能较少。
>
> 重评条件：获得覆盖目标外观和曝光条件的参考 JPEG/RAW 对。

## 10. 阶段 6：计划、拆分和排期

### 10.1 任务要小到可以独立验证

每个任务应说明：

- 对应需求编号。
- 修改范围。
- 明确非范围。
- 实现结果。
- 测试方式。
- 完成标准。
- 依赖和阻塞。

任务过大的信号：

- 同时修改多个无关模块。
- 无法在一句话中说明验收结果。
- 需要数天后才能第一次运行。
- 失败后不知道是哪一部分导致。

### 10.2 里程碑应产生可使用结果

较好的里程碑：

- M1：固定样本可以导入并看到不闪烁的缩略图。
- M2：可以评级、筛选并在重启后保留。
- M3：可以对比、导出并通过核心回归。
- M4：安装包通过发布验证。

较弱的里程碑：

- M1：数据库完成。
- M2：后端完成。
- M3：前端完成。

后者无法尽早证明用户流程可用。

### 10.3 需求就绪定义（Definition of Ready）

任务进入开发前，应满足：

- [ ] 目标和用户价值明确。
- [ ] 范围、非范围和优先级明确。
- [ ] 主要流程和异常流程明确。
- [ ] 验收标准可测试。
- [ ] UI 原型或现有设计规则明确。
- [ ] 数据、兼容和性能约束已检查。
- [ ] 依赖、未知和阻塞已记录。
- [ ] 修改文件范围和不得修改部分已明确。
- [ ] 有测试数据、设备或替代验证方案。

缺少其中一项不一定禁止开发，但必须说明风险和处理方式。

### 10.4 工期估算不是承诺一个精确数字

专业估算通常先拆任务，再给范围和置信度，而不是凭感觉报一个日期。

估算时应分别考虑：

- 已知实现工作。
- 调研和未知风险。
- 接口联调与数据迁移。
- 自动化测试和人工验收。
- 缺陷修复和发布准备。
- 外部设备、样本、审核或授权等待。

推荐用“乐观 / 最可能 / 悲观”三个数表达不确定性，并明确估算前提。高风险未知应先安排预研，不应直接塞进开发工期。中型功能还应为联调、测试和返工保留合理缓冲；缓冲不是偷懒，而是承认软件工作存在不确定性。

当需求或约束变化时，应重新估算，而不是要求原日期保持不变。

### 10.5 团队日常怎样运作：Scrum 与看板

常见团队并不是每天从头讨论全部流程，而是用一个持续维护的任务列表推进：

- **Backlog**：尚未进入开发的需求、缺陷和改进项。
- **Ready**：已经满足需求就绪定义，可以开发。
- **In Progress**：正在实现，必须限制同时进行的数量。
- **Verification**：等待测试、评审或用户验收。
- **Done**：满足完成定义。

Scrum 通常按一到两周的 Sprint 承诺一批目标，并在周期末演示和复盘；看板则持续拉取任务，更适合需求变化频繁或个人项目。两者都强调：优先级透明、进行中工作受限、完成标准一致。

对“你 + Codex”的项目，推荐轻量看板，并把同时开发中的功能限制为 1 个。每天或每次继续任务时只做三件事：

1. 检查当前任务是否被阻塞。
2. 确认是否出现需求变化或新证据。
3. 完成当前切片并验证后，再拉取下一项。

## 11. 阶段 7：开发

### 11.1 正常开发循环

1. 读取权威需求、技术方案和历史决策。
2. 复现当前行为或建立基线。
3. 只修改当前任务需要的部分。
4. 先完成最小垂直切片。
5. 编写或更新自动化测试。
6. 本地运行静态检查和相关测试。
7. 做实际冒烟测试。
8. 审查差异，确认没有无关改动。
9. 更新需求、Spec 和变更记录。
10. 提交清晰、可回滚的版本。

### 11.2 开发中的边界

- 不在开发过程中私自扩大范围。
- 不顺手重构无关代码。
- 不用猜测填补产品决策。
- 不用占位 Demo 冒充完成。
- 不忽略错误、取消、空状态和恢复。
- 不以“在我的电脑上能运行”替代测试。
- 不把测试失败解释成环境问题，除非有证据。

### 11.3 缺陷修复的标准顺序

1. 固定版本和输入。
2. 写出稳定复现步骤。
3. 找到最小根因。
4. 添加能在修复前失败的回归测试。
5. 用最少代码修复。
6. 运行目标测试和邻近回归。
7. 实际重走用户操作。
8. 记录根因和防止复发的约束。

### 11.4 代码审查要看什么

- 是否准确实现了需求，而不是只看代码是否漂亮。
- 是否修改了无关范围。
- 错误、取消和并发是否正确。
- 数据迁移是否可回滚。
- 是否引入性能或安全风险。
- 测试是否真的会在错误行为出现时失败。
- 文档和实际行为是否一致。

### 11.5 完成定义（Definition of Done）

“代码写完”不等于任务完成。一个功能通常只有同时满足以下条件才可以进入 Done：

- [ ] Must 需求和验收场景已经实现。
- [ ] 错误、空状态、取消和恢复已经处理。
- [ ] 相关单元、组件、集成或契约测试已经补充并通过。
- [ ] 缺陷修复具有能防止复发的回归测试。
- [ ] 静态检查、类型检查和目标构建通过。
- [ ] 使用真实入口完成至少一次冒烟测试。
- [ ] 性能、安全、兼容和视觉要求达到本任务门槛。
- [ ] 数据迁移、缓存失效和回滚路径已验证或明确不适用。
- [ ] Spec、需求、API、测试证据和已知限制已经同步。
- [ ] 差异审查确认没有无关文件和顺手重构。
- [ ] 临时文件、调试开关、占位文案和假数据已经清理。
- [ ] 产品负责人可以按验收标准明确判断通过。

发布是更高一级的门禁。单个任务达到 Done，并不代表整个版本已经满足发布条件。

## 12. 阶段 8：测试

### 12.1 测试不是开发结束后的单独步骤

测试设计应在需求阶段开始。因为一条无法测试的需求，通常也是一条没有定义清楚的需求。

### 12.2 测试层次

| 类型 | 主要验证内容 | 例子 |
| --- | --- | --- |
| 单元测试 | 单个函数或规则 | 排序、过滤、状态转换 |
| 组件测试 | 一个 UI 组件 | 按钮禁用、菜单关闭 |
| 集成测试 | 模块之间的协作 | API、数据库、缓存 |
| 契约测试 | 请求和返回格式 | WebView 与后端协议 |
| 端到端测试 | 完整用户流程 | 导入、评级、导出 |
| 视觉测试 | 排版和状态 | 窄窗、dark、缩放 |
| 性能测试 | 时间、内存、I/O | 1000 张首屏 P95 |
| 兼容测试 | 平台和旧数据 | Windows 10/11、旧工作区 |
| 安全测试 | 输入和权限边界 | 路径穿越、令牌、危险删除 |
| 探索测试 | 发现未预料问题 | 快速切换、连续取消 |
| 用户验收 | 是否解决实际工作 | 摄影用户完成真实选片 |

自动化测试擅长防回归，人工测试擅长发现体验和组合问题，两者不能互相替代。

### 12.3 测试用例格式

每个重要用例至少包含：

- 用例编号。
- 对应需求编号。
- 测试环境。
- 前置数据。
- 操作步骤。
- 预期结果。
- 实际结果。
- 证据。
- 通过、失败或阻塞。

### 12.4 测试数据要有代表性

不要只使用“刚好能成功”的数据。应包括：

- 最小和最大规模。
- 空目录。
- 重复文件。
- 损坏文件。
- 不支持格式。
- 超长名称和 Unicode。
- 缺失源文件。
- 横图、竖图、方图和不同方向元数据。
- 不同 RAW 模式。
- 慢磁盘和取消时机。
- 旧版本数据库和缓存。

### 12.5 缺陷严重程度

| 等级 | 定义 | 示例 |
| --- | --- | --- |
| S0 阻断 | 数据损坏、安全事故或应用无法启动 | 永久删除错误目录 |
| S1 严重 | 核心流程无法完成，无合理绕过 | ARW 图片持续闪烁无法选片 |
| S2 一般 | 功能错误但有绕过方式 | 某筛选组合错误 |
| S3 轻微 | 文案、间距或低影响问题 | 个别标签未对齐 |

严重程度表示影响，优先级表示何时修。两者不要混用。

### 12.6 测试退出条件

发布前至少确认：

- [ ] Must 验收标准全部通过。
- [ ] S0、S1 缺陷为零。
- [ ] 核心流程回归通过。
- [ ] 静态检查、类型检查和自动化测试通过。
- [ ] 性能、兼容和安全门禁达到本版本要求。
- [ ] 视觉检查覆盖目标断点和主题。
- [ ] 已知限制已记录且用户可以接受。
- [ ] 测试环境、数据和证据可追溯。

## 13. 阶段 9：用户验收（UAT）

测试通过不等于用户接受。用户验收应使用接近真实工作的场景。

推荐做法：

1. 使用真实但可备份的样本项目。
2. 不给验收者解释内部实现。
3. 按任务目标完成完整流程。
4. 记录阻塞、困惑和绕行。
5. 将反馈分类为缺陷、新需求或偏好。
6. 明确本版本接受、延后或拒绝的事项。
7. 保存验收结论和版本号。

验收反馈不能全部直接变成当前版本修改。先判断它是否违反已确认标准，还是新发现的需求。

## 14. 阶段 10：发布

### 14.1 发布前准备

- 确认版本号和发布范围。
- 冻结发布候选提交。
- 生成目标平台产物。
- 校验依赖和供应链。
- 生成校验和、签名和验证报告。
- 在干净环境安装或解压验证。
- 运行冻结包自检和核心冒烟。
- 准备发布说明、已知限制和升级说明。
- 确认回滚版本和回滚步骤。
- 检查网站、下载地址和版本文案。

### 14.2 发布说明应包含

- 新增内容。
- 修复内容。
- 行为变化。
- 数据或配置迁移。
- 已知限制。
- 支持平台。
- 下载产物和校验方式。
- 回滚注意事项。

### 14.3 发布后验证

- Release 和标签指向正确提交。
- 资产名称和数量符合发布矩阵。
- 校验和匹配。
- 下载链接可以访问。
- 安装后版本号正确。
- 宣传网站已更新。
- 监控没有新增严重错误。

## 15. 阶段 11：监控、维护和复盘

### 15.1 上线后看什么

- 启动成功率。
- 核心任务成功率。
- 错误码和崩溃。
- 首屏和关键操作耗时。
- 任务取消与重试。
- 用户反馈和绕行行为。
- 数据迁移失败。
- 下载和版本分布。

### 15.2 复盘不找人背锅

复盘回答：

- 原计划是什么？
- 实际发生了什么？
- 哪些事实当时不知道？
- 哪个流程本可以更早暴露问题？
- 哪些测试或约束应永久保留？
- 下一次具体改变什么？

例如 ARW 闪烁问题的有效复盘结论不是“以后小心”，而是：

- 预览阶段必须只升不降。
- 相同容器尺寸不得重启渐进流程。
- 图片加载回调不得用数值相同的新对象触发 watcher。
- 必须保留连续切图回归测试和视觉冒烟。

## 16. 变更管理：开发中又想改怎么办

冻结不是拒绝变化，而是让变化有成本和记录。

### 16.1 变更请求至少包含

- 变更原因。
- 原需求和新需求。
- 用户价值。
- 是否阻塞当前发布。
- 影响的页面、接口、数据、测试和文档。
- 工期和风险变化。
- 是否需要迁移或回滚。
- 决策：本版本、下版本、拒绝或待调研。

### 16.2 三种处理方式

| 情况 | 处理 |
| --- | --- |
| 违反已确认验收标准 | 作为缺陷修复 |
| 不违反标准但改善体验 | 评估后作为优化 |
| 增加新能力或改变规则 | 作为新需求走变更 |

### 16.3 防止无限修改的规则

- 当前版本只接收阻断发布或高价值、低风险的变更。
- 其余反馈进入下一版本列表。
- 每次变更必须指出被替换的原决策。
- 原型冻结后，视觉偏好变化不能伪装成缺陷。
- 发布候选冻结后，只修发布阻断问题。

## 17. 特别适合你和 Codex 的协作方式

### 17.1 把一次开发拆成五个明确对话阶段

#### 阶段 A：需求分析

要求 Codex：

- 先读取历史、Spec 和相关代码。
- 复述目标和非目标。
- 找出歧义、风险、约束缺口。
- 给出需要你决定的问题。
- 不写代码。

#### 阶段 B：方案与原型

要求 Codex：

- 给出 1 到 3 个方案和取舍。
- 先做流程和状态，再做视觉。
- 覆盖异常、窄窗、dark 和危险操作。
- 明确推荐方案。
- 不实现未经确认的方案。

#### 阶段 C：实施计划

要求 Codex：

- 明文列出会修改的文件范围。
- 再三说明不得修改的无关范围。
- 把需求映射到任务和测试。
- 定义成功标准和回滚方式。

#### 阶段 D：开发与验证

要求 Codex：

- 先复现缺陷或建立行为基线。
- 用最少代码实现。
- 逐个里程碑验证。
- 报告真实测试结果和限制。
- 不把未验证结果说成完成。

#### 阶段 E：发布

要求 Codex：

- 检查版本、分支、标签和发布矩阵。
- 跑官方门禁。
- 核对资产和校验和。
- 最后更新网站和线上链接。

一次对话可以跨越多个阶段，但必须明确当前处于哪一阶段。

### 17.2 你提供给 Codex 的最佳材料

- 当前版本和分支。
- 权威需求文档位置。
- 截图或录屏。
- 可复现的样本数据。
- 真实设备和环境信息。
- 期望结果与不可接受结果。
- 本次必须做和明确不做。
- 性能或质量门槛。
- 是否允许改数据库、接口、发布矩阵。
- 是否允许删除、移动或覆盖文件。

材料不完整时，可以先让 Codex做需求审计，不要直接说“按你理解实现”。

    4. 1 到 3 个方案及取舍；
    5. 可测试的验收标准草案；
    6. 本次可能涉及的文件范围，并明确不得修改的无关部分。

    在我确认需求和原型前，不要开始实现，不要用猜测补齐未知。

## 18. 用 ARW 模块说明“约束为什么会漏”

### 18.1 “封面取第一张图片”仍然不够完整

至少还需要确认：

- 第一张按导入顺序、文件名、拍摄时间还是当前排序？
- 同值时用什么字段稳定排序？
- 取 ARW 内嵌缩略图还是配对 JPG？
- 方向怎样处理？
- 第一张损坏、丢失或不支持时怎样回退？
- 第一张被永久删除后是否自动换封面？
- 新导入一张更早的图片后是否改变封面？
- 用户能否手动指定并覆盖默认规则？
- 封面是否持久化和缓存？
- 项目卡片加载失败时是否保留旧封面？
- 窄窗、dark 和高 DPI 下怎样裁切？

一个更完整的第一版规则可以是：

> 默认封面取项目成员按拍摄时间升序、规范化路径升序稳定排序后的第一张有效成员缩略图。没有拍摄时间时回退到文件修改时间。首成员无可用缩略图时顺序尝试下一成员；全部失败时显示固定占位。删除、重新绑定或源版本变化后异步刷新，刷新成功前保留旧封面。第一版不支持手动更换封面。

这段规则是否正确仍需产品负责人确认，但已经可以写测试。

### 18.2 “创意外观无法使用”可能是三种不同问题

1. 原本应该可用，但按钮或接口坏了：这是缺陷。
2. 因没有可信校准数据而主动禁用：这是已知限制。
3. 用户现在要求增加近似外观：这是新需求和产品风险。

如果不先分类，开发者可能把安全禁用误修成“随便给一组颜色参数”，结果功能看起来能点，但输出不可信。

### 18.3 “图片闪烁”不是一句 CSS 问题

需要定义：

- 闪烁发生在缩略图、预览还是两者。
- 是否在低清替换高清时出现。
- 是空白、尺寸跳动、方向变化还是清晰度降级。
- 连续切换、窗口缩放、比较模式是否触发。
- 已显示最佳预览是否允许回退。
- 旧请求晚到时能否覆盖新选择。
- 预加载失败时保留什么。

只有这些状态明确后，才能建立稳定的回归测试。

## 19. 建议的项目文档体系

权威信息应各归其位，避免同一规则散落在聊天里。

    docs/
      spec.md                         项目架构、全局约束、发布边界
      development-workflow-guide.md   本手册
      requirements/
        feature-name.md               单个功能的权威需求
      designs/
        feature-name-ux.md            流程、原型和状态
        feature-name-tech.md          技术方案
      adr/
        0001-decision-name.md         重要且长期的技术/产品决策
      test-plans/
        feature-name.md               测试矩阵与验收证据
      releases/
        0.3.0.md                      版本范围、限制和验证

不必马上重组现有目录。重要的是以后每个结论有唯一权威来源，并在 AGENTS.md 中建立索引。

文档状态建议统一为：

- 草案。
- 待确认。
- 已确认。
- 开发中。
- 验收中。
- 已发布。
- 已废弃。

每份权威文档至少写版本、状态、最后更新时间和负责人。

## 20. 按任务大小选择流程，不要过度管理

### 20.1 小缺陷（数小时内）

需要：

- 缺陷卡。
- 稳定复现。
- 根因。
- 回归测试。
- 冒烟测试。

通常不需要完整原型和长技术方案。

### 20.2 小功能（约 1 到 3 天）

需要：

- 一页需求。
- 简单流程或线框。
- 验收标准。
- 文件范围。
- 相关自动化测试和冒烟。

### 20.3 中型功能（约 1 到 2 周）

需要：

- 立项说明。
- 完整需求和原型。
- 技术方案。
- 里程碑。
- 测试计划。
- 用户验收和发布计划。

### 20.4 大型或高风险功能

应拆成多个可独立发布的中型里程碑，并增加：

- 正式预研。
- 数据迁移演练。
- 性能基准。
- 安全审查。
- 灰度或回滚机制。

## 21. 一套你可以从下次开始执行的轻量节奏

### 开发前：30 到 60 分钟需求审计

1. 写出目标、非目标和用户场景。
2. 按约束清单逐项检查。
3. 标出 Must、Should、Could、Won't。
4. 列出未知和所需证据。
5. 生成验收场景。

### 原型阶段：先流程，后视觉

1. 先确认入口和任务步骤。
2. 再确认页面结构。
3. 补齐所有状态。
4. 检查窄窗和 dark。
5. 冻结原型版本。

### 开发阶段：按垂直切片交付

1. 每个切片都可以运行。
2. 每个切片都有测试。
3. 每个切片都检查无关改动。
4. 发现新需求先记录，不立即混入。

### 验收阶段：按场景，不凭感觉

1. 用真实样本执行完整任务。
2. 对照需求编号逐项通过。
3. 反馈分类。
4. 明确接受的已知限制。

### 发布阶段：自动门禁 + 线上复核

1. 冻结提交和标签。
2. 官方流水线构建。
3. 核对资产和校验和。
4. 更新网站。
5. 检查真实下载和安装。

## 23. 最重要的实践原则

1. **先确认问题，再讨论方案。**
2. **先定义不做什么，再开始做。**
3. **先写验收标准，再写代码。**
4. **先做流程和状态，再做漂亮界面。**
5. **高风险未知先试验，不能靠猜。**
6. **一次只改变一个清晰范围。**
7. **所有新变化都要说明影响和版本归属。**
8. **自动化测试防回归，真实冒烟验证可用性。**
9. **发布不是编译成功，而是产物、安装、链接和回滚都成立。**
10. **聊天不是权威需求，确认后的文档才是。**

你不需要一下子成为专业产品经理或工程经理。下一次迭代只要做到三件事，就会明显顺畅：

1. 开发前使用本手册的需求模板。
2. 在编码前冻结流程、状态和验收标准。
3. 将开发中新出现的想法放入变更列表，而不是立即混入当前任务。

这样仍然会有迭代，但迭代会从“反复返工”变成“有记录、有取舍、可预测的产品演进”。
