# 个人软件轻量开发指南

- 状态：长期维护
- 适用对象：软件所有者与 Codex
- 目标：用最少流程完成可靠、可验证的开发

## 1. 基本原则

1. 先说清问题和预期结果，再开始修改。
2. 不清楚时及时提问，不用猜测补齐需求。
3. 只修改完成当前任务必需的部分，不顺手重构或扩展功能。
4. 修复缺陷时先复现；无法复现时先收集证据或做最小诊断。
5. 实现后运行相关测试，并至少做一次冒烟测试。
6. 未验证的结果不能作为已完成交付。
7. 高风险或难以撤销的操作必须先确认。

个人项目不需要模拟团队审批。需求说明、实现计划、测试记录可以直接写在当前任务中，不要求为每一步单独建立文档。

## 2. 开始任务前

### 2.1 先确认四件事

- **目标**：完成后应发生什么变化。
- **范围**：本次必须做什么。
- **非范围**：容易被误解、但本次明确不做什么。
- **成功标准**：怎样判断任务已经完成。

简单且明确的任务可以用几句话说明，不需要正式 PRD。只有存在会明显改变实现结果的歧义时才暂停并询问；能够从代码、现有 Spec 或测试中查明的内容应先自行调查。

### 2.2 明确修改范围

实施前说明预计涉及的文件或模块，不得修改无关部分。

发现无关问题时只报告，不在当前任务中顺手处理。工作区已有的用户改动和其他会话改动必须保留。

### 2.3 何时需要先讨论方案

以下情况先给出简短方案和取舍，得到确认后再实施：

- 存在两种以上会产生明显不同体验或长期成本的理解。
- 需要改变架构、公开接口、数据格式或兼容范围。
- 涉及数据迁移、删除、覆盖、不可逆操作、安全或隐私。
- 需要改变发布矩阵或新增外部服务、付费依赖。
- UI 主流程、信息结构或核心交互尚未确定。

普通实现细节不需要逐项审批，选择与现有代码一致的最简单方案即可。

## 3. 按风险选择流程

流程由风险决定，不按功能大小机械套模板。

### 3.1 低风险任务

例如文案调整、局部样式、小型配置修改或原因明确的简单缺陷。

流程：

1. 确认目标和修改范围。
2. 修改最少代码。
3. 运行相关检查。
4. 做一次冒烟测试。

不要求另写需求文档、原型、技术方案或测试报告。

### 3.2 普通任务

例如新增独立功能、修改多处行为或修复需要调查的缺陷。

流程：

1. 查看现有 Spec、相关代码和测试。
2. 写一个简短计划，列出验证项。
3. 明确主要流程、边界情况和成功标准。
4. 分步实现并运行相关测试。
5. 用真实或有代表性的数据完成冒烟测试。

### 3.3 高风险任务

符合以下任一条件即按高风险处理：

- 可能损坏或丢失用户数据。
- 数据库、缓存、配置或文件格式需要迁移。
- 涉及认证、安全、隐私或危险文件操作。
- 影响大量数据时的性能或稳定性。
- 改变公开接口、跨平台兼容性或发布矩阵。
- 失败后难以回滚。

高风险任务需要：

1. 先验证关键未知项。
2. 说明风险、回滚方法和验证方法。
3. 对危险或不可逆操作取得明确确认。
4. 增加针对风险的自动化测试或可重复验证。

## 4. 实现与验证

### 4.1 实现规则

- 使用能解决问题的最少代码。
- 匹配现有架构、模块边界和代码风格。
- 不添加未要求的功能、配置、抽象或猜测性错误处理。
- 不清理无关代码、注释或格式。
- 每一项改动都应能追溯到当前需求。
- 可以拆成清晰业务模块时合理解耦，但不为了形式上的单一职责过度拆分。

### 4.2 缺陷修复

1. 记录可观察到的问题。
2. 稳定复现，或说明为什么暂时无法复现。
3. 找到根因，不用掩盖症状的补丁代替根因修复。
4. 添加能防止复发的测试；无法自动化时说明原因。
5. 重跑复现步骤和相关回归测试。

### 4.3 最低验证要求

每项开发至少完成：

- 与改动直接相关的自动化测试或静态检查。
- 一次代码级、命令行或真实界面的冒烟测试。
- 检查 Git diff，确认没有无关改动。

具体检查按项目现有工具执行，例如 Ruff、mypy、pytest、vitest、类型检查或构建。不要为了一个局部改动机械运行所有耗时检查；但影响发布、公共基础模块或多端行为时，应扩大回归范围。

测试失败时必须如实说明失败项和影响，不能把未运行、被跳过或假设通过写成“验证完成”。

## 5. UI 任务附加要求

任何前端或客户端修改都视为 UI 任务，并在通用流程外增加以下检查：

- 先保证任务流程和信息层级清楚，再处理视觉细节。
- 响应式适配移动端，优先使用 flex 或 grid。
- 使用语义化元素，文本对比度充足，同行同列元素对齐。
- 支持 light、dark 和跟随系统主题。
- 弹出式菜单可通过点击外部收起。
- 不使用无功能目的的装饰，不使用蓝紫渐变作为视觉重点，不做卡片套卡片。
- 新项目先定义基础 CSS token，并使用 8pt 网格，必要时兼容 4pt 和 12pt。
- 交付前必须通过浏览器截图或其他可视化方式检查实际界面。

复杂表单放在二级页面或模态中，一级页面只保留入口。若现有设计系统与上述规则冲突，应先指出冲突，再决定是保持一致还是调整设计系统。

## 6. Spec 与其他文档

Spec 只记录长期有效、以后开发仍需要遵守的事实。出现以下变化时更新对应 Spec：

- 项目架构或模块职责。
- 对外接口或长期产品行为。
- 数据库、配置、缓存或文件格式。
- 支持平台、兼容范围或发布约束。
- 重要且容易被以后修改破坏的技术决策。

普通缺陷修复、局部样式调整、实现细节或一次性调查不要求更新 Spec。不要为了留下流程痕迹而创建重复的 PRD、测试报告、验收记录或复盘文档。

若需要更新 Spec，应修改现有权威文档；只有没有合适位置时才新建文档，并在项目 `AGENTS.md` 的 Spec 索引中维护入口。

## 7. 发布

只有用户要求发布或任务明确包含发布时，才执行完整发布流程。普通开发完成不等于自动发布。

发布前至少确认：

- 版本号、目标平台和发布矩阵正确。
- 官方构建与测试通过。
- 产物名称、数量、校验和及安装结果正确。
- 发布说明列出主要变化和已知限制。
- 下载链接可用，必要时具备回滚方法。

发布矩阵属于强约束，未经用户明确批准不得修改。

## 8. 收尾

任务完成时：

1. 汇总实际修改和验证结果。
2. 说明仍存在的限制或未解决问题。
3. 检查是否有其他 Codex 会话正在修改同一项目；有则避免冲突并按项目规则处理。
4. 在不包含用户无关改动的前提下，为本次任务创建一次 Git commit。
5. 较大功能且配置了远程仓库时，询问是否需要推送。

最终判断只有三个问题：

- 目标是否真的实现？
- 相关行为是否经过验证？
- 是否只修改了应该修改的部分？
