## TC-001：扩大推荐去重历史并修正“最近入库”重复

### 背景

推荐页每批返回 15 张图片。当前每个 viewer 只读取最近 60 张已成功展示图片作为排除历史，相当于仅覆盖 4 个完整批次；第 5 批开始，最早一批图片会重新获得推荐资格。

现有数据验证结果：

- 桌面 viewer 的 17 个批次共返回 255 张图片，其中只有 202 个唯一 SHA-256，产生 53 次重复推荐。
- 45 次重复恰好间隔 5 个批次发生，46 次属于 `recent` 槽位再次进入 `recent` 槽位。
- LAN viewer 同样出现以 5 个批次为主要间隔的重复。
- 同一批次内部不存在 SHA-256、文档 ID 或候选 ID 重复，`shown` 事件也已正常写入。

因此问题不是推荐事件丢失或数据库只保存 60 条记录，而是去重历史的读取上限过小，且 `recent` 槽位只按入库时间排序，历史窗口放开后会重新选择同一组最新图片。

### 目标与成功标准

- 每个 viewer 的强去重历史至少覆盖 200 张已成功展示的图片。
- 采用 240 张历史窗口，覆盖 16 个完整批次。
- 候选充足且每个批次均成功提交 `shown` 时，最近 16 个批次内不得出现相同 SHA-256。
- `recent` 槽位存在未展示候选时，不得优先返回已经展示过的图片。
- `random` 槽位存在未展示候选时，不得因随机种子排序而优先返回已经展示过的图片。
- 候选不足时允许逐级缩小排除窗口或返回部分批次，但同一批次内仍不得复制图片补足数量。
- 保持 viewer 隔离、请求幂等、曝光计数和现有推荐配额不变。

### 技术方案

1. 将推荐历史读取上限从 60 调整为 240。
2. 将历史排除窗口调整为 `240 → 210 → 180 → 150 → 120 → 90 → 60 → 30 → 0`，仅在候选不足以组成完整批次时逐级放宽。
3. `recent` 槽位每次选择严格限定在当前最低 viewer 展示次数层级，再按 `mtime_ns` 降序和稳定候选 ID 排序，避免后续多样性评分越级选回高曝光候选。
4. `random` 槽位每次选择严格限定在当前最低 viewer 展示次数层级，再使用现有请求种子执行稳定随机排序。
5. 将每个候选池的采样上限从 100 调整为 256，避免扩大历史窗口后候选池本身被完全排除。继续保持有界采样，不执行全库随机排序或全量加载。
6. 继续复用现有 `events` 和 `content_stats` 数据，不修改 SQLite 表结构，不迁移或清空既有推荐历史。

### 修改范围

实现时仅允许修改以下范围：

- `image_vector_service/recommendation_store.py`：历史读取上限。
- `image_vector_service/recommendations.py`：排除窗口以及 `recent`、`random` 排序规则。
- `image_vector_service/backend_server.py`：候选池采样上限。
- `tests/test_recommendation_store.py`、`tests/test_recommendations.py`、`tests/test_recommendation_backend.py` 和受采样参数直接影响的既有推荐测试。
- `docs/spec.md`：实现完成后同步最终行为。

不得修改前端、数据库 Schema、图片索引、搜索、智能标注、发布矩阵或其他无关模块；不得借本项改动顺手重构推荐代码。

### 验证项

- 单元测试：240 条历史可按最近成功展示顺序读取，viewer 之间互不影响。
- 算法测试：连续生成并标记至少 17 个批次，前 16 个批次不存在相同 SHA-256。
- 排序测试：`recent` 和 `random` 均优先选择未展示或低曝光候选。
- 降级测试：不足 15 个合格候选时逐级缩小窗口，最终仍不足则返回 `partial`，且批次内无重复。
- 幂等测试：相同 `request_id` 继续回放原批次，不新建不同队列。
- 冒烟测试：使用本地推荐数据库连续刷新推荐页，核对批次数量、`shown` 事件以及 SHA-256 重复间隔。

### 本项不包含

- 不合并桌面端与 Android/LAN viewer 的推荐历史；跨设备仍按现行设计隔离。
- 不在本项中增加跨批次相册或角色冷却。若仍需降低“不同文件但画面相似”的重复感，应另立改动项讨论相册配额、角色配额或向量相似历史。
- 不删除、重写或清空现有推荐记录。

## TC-002：为图片推荐增加单张右键菜单

### 背景

TC-002 实施前，Windows 图片推荐页只在卡片底部提供“打开、喜欢、导出、不喜欢”按钮，推荐图片本身没有右键菜单。搜索结果页已有右键操作，但其中“相关/不相关”表示图片与当前查询的相关性，并绑定搜索结果的多选状态，不能直接照搬为推荐偏好。

### 目标与成功标准

- 在 Windows 图片推荐页右键任意推荐图片时，打开只针对该图片的操作菜单。
- 菜单提供：打开详情、系统打开、所在文件夹、喜欢、不喜欢、复制图片、复制文件、复制文件路径、导出到文件夹。
- 推荐菜单使用“喜欢/不喜欢”及现有 `like/dislike` action；搜索结果菜单继续使用“相关/不相关”，不得改变搜索学习语义。
- “喜欢”和“不喜欢”互斥，并正确显示当前批次内该图片的最新偏好状态；操作失败时保持原状态并显示现有错误提示。
- 系统打开成功后继续记录 `open`，导出实际成功后继续记录 `export`；打开详情和复制操作不新增后端 action 类型。
- 菜单必须限制在可视窗口内，并支持点击菜单外、按 Escape、窗口缩放或切换页面时收起。
- 原生操作进行期间防止对同一图片重复提交。
- 推荐卡片仅显示图片与图片右下角的推荐来源角标；移除图片下方的文件名、图库名和“打开/喜欢/导出/不喜欢”按钮。单击图片继续打开，右键菜单、推荐详情及其中既有操作保持不变。

### 交互范围

- 右键只定位当前图片，不创建推荐页多选状态。
- 不显示“已选择 N 张”“支持 Ctrl / Shift 跨页保留选择”和“清除选择”。
- 不支持 Ctrl/Shift 多选或批量复制、批量导出。
- “复制文件”和“导出到文件夹”均只处理当前右键图片。
- 打开详情使用推荐结果已有的预览图、文件名、图库、推荐来源、标签、尺寸和文件大小；不得伪造搜索匹配度、搜索排名或查询相关性字段。

### 技术方案

1. 推荐卡片删除图片下方的信息和按钮区域，仅保留可单击、可右键的图片及图片右下角来源角标；捕获 `contextmenu`，阻止浏览器默认菜单，并保存当前 `RecommendationItem` 与经过窗口边界约束的菜单坐标。
2. 扩展现有图片右键菜单组件的单张模式和反馈文案配置：搜索场景保持现有结构，推荐场景隐藏多选提示、撤销搜索反馈和清除选择，并发出 `like/dislike` 事件。
3. 推荐页通过现有 `useRecommendations.recordAction` 提交 `like/dislike`，复用当前 pending、重试 event ID 和偏好状态逻辑，不新增推荐 API。
4. 通过 `App.vue` 将现有原生图片操作按单张回调传给推荐页，复用 `mediaId` 执行系统打开、定位文件、复制图片、复制文件、复制路径和导出。
5. 推荐详情使用 feature 内独立详情视图，仅读取 `RecommendationItem` 已有字段，避免把推荐结果伪装成 `SearchResultItem` 或改动搜索详情语义。

### 修改范围

实现时仅允许修改以下范围：

- `frontend/src/features/recommendations/__tests__/RecommendationPage.spec.ts`、推荐详情测试、右键菜单组件测试及受新增 props 直接影响的 `App` 测试。
- `docs/spec.md`：实现完成后同步最终交互契约。

不得修改推荐后端 action 集合、数据库 Schema、搜索反馈含义、Android 推荐页、推荐选择算法、发布矩阵或其他无关模块；不得借本项改动重构整个图库菜单或原生操作层。

### 验证项

- 组件测试：右键推荐图片打开菜单，菜单目标和坐标正确，浏览器默认菜单被阻止。
- 卡片测试：仅渲染图片和推荐来源角标，不渲染文件名、图库名或底部操作按钮；单击图片仍触发现有打开行为。
- 文案测试：推荐场景显示“喜欢/不喜欢”，搜索场景仍显示“相关/不相关”。
- 状态测试：喜欢和不喜欢互斥，pending 期间禁用重复操作，失败后不误改状态。
- 原生操作测试：系统打开、定位、三种复制和导出均只收到当前图片的 `mediaId`；仅成功打开和成功导出记录对应推荐 action。
- 收起测试：点击其他区域、Escape、窗口缩放和离开推荐页均关闭菜单。
- 详情测试：仅展示推荐结果已有字段，关闭、系统打开和定位文件可用。
- 视觉检查：在 light mode、dark mode 和窄窗口下截图检查菜单边界、对齐、文本对比度及详情布局。

### 本项不包含

- 不新增撤销推荐偏好的后端接口。

## TC-003：修正 Android 推荐查看与反馈交互

### 背景

Android 推荐页存在三个关联的交互问题：

- 推荐页进入全屏图片查看器后，系统返回或关闭查看器会回到“搜索”Tab，而不是来源“推荐”Tab。
- 推荐网格卡片直接显示“喜欢/不喜欢”，用户尚未查看原图细节即可反馈。
- 全屏查看器长按打开底部菜单后，点击“喜欢”或“不喜欢”只提交反馈，菜单不会收起。

返回页错误的直接原因是 `SearchScreen` 在内部使用 `remember` 保存 `selectedTab`，而全屏查看器通过 `ZvecApp` 的提前返回替换整个 `SearchScreen`。关闭查看器后 `SearchScreen` 被重新创建，Tab 默认值重新变为 `SEARCH`。搜索结果因另有搜索结果副作用会再次切换到结果页，推荐页没有对应恢复逻辑。

### 目标与成功标准

- 从 Android 推荐 Tab 打开任意图片后，通过系统返回手势、系统返回键或查看器关闭操作退出时，必须回到推荐 Tab。
- 返回推荐 Tab 后保留原推荐批次、滚动数据和已加载图片，不重新生成批次，也不跳转到搜索或结果 Tab。
- 推荐网格卡片不再显示“喜欢/不喜欢”或反馈状态，点击卡片只进入全屏查看器。
- 推荐反馈仅保留在全屏查看器的长按底部菜单中，使用户先查看图片再决定喜欢或不喜欢。
- 在长按菜单点击“喜欢”或“不喜欢”后立即收起菜单，再异步提交且只提交一次对应 action。
- 搜索结果查看器的返回行为、保存、分享、旋转和详细信息操作保持不变。

### 技术方案

1. 将 `MobileTab` 选择状态提升到不会因全屏查看器提前返回而离开组合的位置，即 `ZvecApp` 根级的 `rememberSaveable` 状态；`SearchScreen` 改为接收当前 Tab 和切换回调。
2. 将推荐网格 `LazyGridState` 同样提升到 `ZvecApp`，打开推荐查看器时保留当前 `RECOMMENDATIONS` Tab、原批次和滚动位置；`closeViewer` 仍只清理 viewer source、index 和传输状态，不通过推荐数据存在与否猜测返回页。
3. 从 `RecommendationCard` 删除 reaction、pending、`onLike`、`onDislike` 参数和按钮区域；`RecommendationPanel` 不再向卡片传递列表内反馈回调。
4. 全屏查看器继续只为 `RecommendationItem` 在长按菜单显示“喜欢/不喜欢”。两个按钮均先将 `sheetItem` 设为 `null` 关闭 `ModalBottomSheet`，随后调用现有 `onReaction`。
5. 继续复用 `AppViewModel.reactToRecommendation` 的 pending、幂等 event ID 和错误恢复逻辑，不新增 action、接口或持久化字段。

### 修改范围

实现时仅允许修改以下范围：

- `android/app/src/main/java/com/zvec/lanviewer/ui/ZvecApp.kt`：Tab 状态提升、推荐卡片按钮移除和长按菜单收起顺序。
- 与上述交互直接对应的 Android Compose UI/状态测试；若新增测试文件，仅放在 `android/app/src/androidTest/java/com/zvec/lanviewer/ui/` 或现有 Android UI 单元测试目录。
- `docs/spec.md`：实现完成后同步 Android 推荐交互。

原则上不需要修改 `AppViewModel.kt`、网络层或数据模型。不得修改 Windows 推荐页、推荐后端、数据库 Schema、推荐选择算法、搜索流程、发布矩阵或其他无关部分；不得为本项引入新的导航框架。

### 验证项

- 导航测试：推荐 Tab → 打开推荐图片 → 系统返回，断言仍显示推荐 Tab 和原批次。
- 导航回归：结果 Tab → 打开搜索结果 → 系统返回，仍显示结果 Tab。
- 列表测试：推荐卡片不包含“喜欢”“不喜欢”“已喜欢”或“已跳过”按钮，点击图片仍打开正确索引。
- 菜单测试：推荐原图长按显示喜欢/不喜欢；搜索结果原图长按不显示推荐反馈。
- 收起测试：点击喜欢或不喜欢后 `ModalBottomSheet` 立即消失，并只发送一次对应 action；网络请求尚未完成时也不得保持菜单展开。
- 回归测试：保存和分享仍先收起菜单；旋转和详细信息仍可在菜单内连续操作。
- 视觉检查：在 Android light mode、dark mode 和窄屏设备上截图，确认移除按钮后的卡片信息密度与对齐正常。
- 冒烟测试：在 Android 真机或模拟器上完成“推荐 → 查看原图 → 长按 → 喜欢 → 返回推荐”的完整流程。

### 本项不包含

- 本项不定义或修改 Windows 推荐卡片交互；Windows 最终行为以 TC-002 为准。
- 不取消推荐系统的 `like/dislike` action，只调整 Android 的反馈入口。
- 不在推荐网格卡片上新增长按菜单；长按菜单仍属于全屏原图查看器。
- 不改变点击推荐图片时现有的 `open` action 记录。

## TC-004：跨桌面与 Android 共享个性化推荐偏好

### 背景

桌面端和 Android 当前都会把推荐 `like/dislike` action 写入电脑端 `recommendations.sqlite3`，但事件按 viewer 标识记录，客户端只在当前内存状态中显示反馈结果，推荐选择算法也不读取这些偏好。用户已明确要求桌面和手机共享同一套偏好。

共享范围限定为显式偏好：所有连接到同一台 YaoLens 后端且已获授权的客户端共同使用一个默认偏好档案。批次、`shown` 历史和曝光次数继续按 viewer 隔离，不能因共享偏好而合并各设备的浏览历史。

### 目标与成功标准

- 桌面和所有已授权 Android 设备共享同一套图片喜欢/不喜欢状态。
- 同一 SHA-256 在不同设备产生冲突反馈时，以电脑数据库中最后成功写入的 `like/dislike` 事件为最终状态。
- 现有历史 `like/dislike` 事件直接参与共享偏好，不要求用户重新反馈，也不得清空或重写原事件。
- 已明确喜欢或不喜欢的原图不再向任何设备重复推荐；喜欢图片仅用于提升相似且未展示图片，不喜欢图片用于降低相似图片排序。
- 个性化只读取明确的 `like/dislike`。`shown` 仅用于曝光与历史去重，`open` 只表示查看，`export` 继续作为操作事件但不在本项中推断为喜欢。
- 至少累计 10 张具有最终显式偏好的不同图片后启用个性化；强度随有效反馈增加并设置上限，不允许少量反馈立即主导整批结果。
- 保持技术质量、最近入库、低曝光和随机发现的固定配额；随机发现继续承担探索职责，不按偏好向量改造成同质化推荐。
- 个性化不得临时调用模型，不保存图片路径或向量到推荐数据库，只复用各图库已经存在的图片向量。
- 客户端重启或更换设备后，服务端返回的最终偏好仍可恢复“已喜欢/已不喜欢”状态。

### 偏好与排序规则

1. 共享档案固定属于当前电脑端 YaoLens 实例，不新增用户账号。事件仍保留原 `viewer_id` 作为操作来源，但计算最终偏好时跨 viewer 合并。
2. 对每个 SHA-256，只取 sequence 最大的 `like/dislike` 事件作为当前偏好；历史重复点击不会增加该图片在画像中的权重。
3. 生成推荐前先排除所有已有最终显式偏好的原图，再应用 TC-001 的 viewer 展示历史排除，避免喜欢过的图片因个性化加分而反复出现。
4. 从有可用现有向量的喜欢图片生成正向偏好画像，从不喜欢图片生成负向偏好画像；已删除、向量缺失或向量空间不兼容的反馈仍保留最终状态，但不参与向量画像。
5. 个性化仅在 `quality`、`recent` 和 `low_exposure` 候选内部提供有上限的排序加减分，再继续执行现有相册/角色配额和向量多样性惩罚。`random` 保持稳定随机排序。
6. 有效反馈不足 10 张、没有可用偏好向量或跨图库向量空间不兼容时，回退到现行非个性化排序，并在响应中给出不含隐私数据的原因。
7. 个性化强度固定为 `min(0.25, effective_count × 0.005)`：10 条有效向量反馈时为 5%，50 条起达到 25% 上限。喜欢与不喜欢分别生成单位向量均值画像，候选 affinity 为可用正向相似度与负向相似度取反后的均值，最终调整严格限制在 `[-0.25, +0.25]`，并由确定性测试固定。

### 数据与接口方案

- 继续以现有 `events` 和 `items` 为事实来源，通过 `item_id` 关联 SHA-256、library ID 和 doc ID，并按事件 sequence 计算每张图片的最终共享偏好。
- 不新增偏好表，不改变现有四表 Schema。实测 `EXPLAIN QUERY PLAN` 后增加精确候选偏好查询使用的 `idx_items_sha256`、`idx_events_item_action_sequence`，以及有界画像事件倒序读取使用的部分覆盖索引 `idx_events_preference_sequence`；未被 planner 使用的候选索引不保留。
- 推荐画像按 sequence 倒序最多扫描最近 4096 条 `like/dislike` 事件，在该有界窗口内按 SHA-256 首次出现取最终状态并最多保留 256 张，再按图库 worker 读取现有向量，不能跨线程直接访问 Collection。禁止新增偏好表意味着无法同时保证固定读取工作量与任意重复历史下始终凑满全历史最新 256 个不同 SHA；极端重复反馈只让较旧图片退出画像并安全降级，不影响全历史最终偏好、原图排除或批次回放的精确性。
- 推荐响应为每个当前批次项增加可选最终偏好字段，并返回个性化是否应用、有效反馈数和安全原因码。降级码为 `insufficient_preferences`、`vectors_unavailable`、`incompatible_vector_spaces`；幂等批次回放使用 `replayed` 且仍读取 item 当前最终偏好。action 成功响应同样返回与事件写入原子读取的当前最终偏好，避免较旧 event ID 在跨设备冲突后回放时覆盖客户端显示。不得返回其他设备 ID 或完整反馈历史。
- Windows 与 Android 均以服务端偏好为准恢复显示状态。手机不另建一套独立偏好数据库，成功提交到电脑后即对所有设备生效。
- 相同 `event_id` 继续保持幂等；网络失败不得提前在客户端永久显示成功状态。

### 修改范围

实施核验发现，backend 已返回 action 幂等结果，但 Windows 与 LAN 两层 facade
会丢弃该结果；若不贯通 action 最终偏好，旧 event ID 在跨设备冲突后回放时

## TC-005：移除“最近入库”推荐来源

### 背景

TC-001 将 viewer 去重历史扩大到 240 张，并让原 `recent` 槽位优先选择低曝光候选，但该槽位仍会持续围绕入库时间最新的一小组图片排序；历史窗口在候选不足时放宽后，这组图片仍容易再次出现。用户已明确不需要“最近入库”作为独立推荐来源，因此本项移除算法槽位，而不是只隐藏前端角标。

### 目标与成功标准

- 新生成的推荐批次不再包含 `bucket=recent`，界面不再出现“最近入库”文案。
- 每批仍保持 15 张，固定配额调整为技术质量 5、低曝光 6、随机发现 4。
- 移除按 `mtime_ns` 倒序读取的最近入库候选采样，避免继续为已取消来源加载候选。
- `low_exposure` 和 `random` 在存在未展示候选时，不得因个性化或向量多样性评分越级选回已展示候选。
- 升级前已经持久化的 `recent` 批次仍可幂等回放；旧项不得被过滤或导致解析失败，Windows 显示通用“推荐”，Android 继续安全读取。
- 不清空推荐数据库，不迁移或重写旧批次、shown 历史和反馈事件。

### 技术方案

1. 从活动推荐槽位与固定配额中删除 `recent`，将其 4 张配额分配为 `low_exposure +2`、`random +2`，总数保持 15。
2. 候选采样只保留技术质量池和稳定随机池；低曝光排序继续基于这两个有界候选池的并集及 viewer 曝光计数，不增加全库扫描。
3. 将最低曝光层级的硬约束从原 `recent` 转移到 `low_exposure`，并保留 `random` 的同类约束；个性化只作用于 `quality` 与 `low_exposure`。
4. 推荐数据库中的 `slot` 继续按字符串保存且不做 Schema 变更。批次回放链路继续接受旧 `recent`，但新选择器永远不生成该值。
5. Windows 客户端保留对旧 `recent` wire value 的解析兼容，来源角标和详情统一显示为“推荐”；Android 的字符串 bucket 与带默认值的 quota 模型保持兼容，新契约不再返回活动 `recent` 配额。

### 修改范围

本项仅允许修改以下位置：

- `image_vector_service/recommendations.py`：活动槽位、配额及低曝光选择约束。
- `image_vector_service/state.py`：删除最近入库候选查询。
- `frontend/src/features/recommendations/RecommendationPage.vue`、`RecommendationDetail.vue`、`useRecommendations.ts`：移除用户可见文案并保留旧批次兼容。
- 与上述行为直接对应的 Python、Windows 和 Android 推荐测试。
- `docs/spec.md`、`docs/android-lan-api-v1.md`、`docs/technical-changes.md` 与推荐说明文案。

不得修改 `recommendation_store` Schema、240 张去重历史、共享偏好语义、搜索流程、图片索引模型、发布矩阵或其他无关部分；再次强调，不得借本项修改无关页面、格式或邻近代码。

### 验证项

- 算法测试：完整批次配额为 5/6/4，所有新项均不含 `recent`。
- 候选测试：每图库候选上限从三池并集降为两池并集，仍同时覆盖技术质量与稳定随机候选。
- 排序测试：`low_exposure` 和 `random` 均不会在未展示候选存在时被 MMR 越级到更高曝光层级。
- 回放测试：数据库中已有 `recent` 项可经后端和 Windows 客户端读取，并只显示通用“推荐”。
- Android 契约测试：缺少 `recent` quota 字段时使用兼容默认值并正确读取 5/6/4 新配额。
- 冒烟测试：连续生成批次，确认响应、Windows 推荐页和 Android 推荐页均不出现“最近入库”。

### 本项不包含

- 不删除旧批次或旧事件。
- 不改变批次大小、240 张历史窗口、相册/角色限制或显式偏好排除。
- 不在本项中实施 MMR 向量归一化缓存、偏好画像缓存或其他独立性能优化。

## TC-006：优化推荐候选、向量选择与偏好画像性能

### 背景与基线

TC-005 后的纯选择基线使用 `tools/benchmark_recommendations.py`、固定种子 `20260803`、候选构造不计时、预热 3 次并正式运行 10 次。当前机器实测如下：

- 300 候选 × 1024 维：中位数 1412.339 ms，P95 1481.323 ms。
- 768 候选 × 1024 维：中位数 3818.171 ms，P95 3846.726 ms。

现行实现为每个图库固定读取每类 256 个候选；每选择一个槽位都会重新执行基础排序，并让每个剩余候选与全部已选项重新计算余弦和向量范数；每次换批也会重新读取最多 256 个偏好向量并重建画像。这些重复工作不改变结果，却直接放大候选规模和向量维度带来的延迟。

### 目标与成功标准

- 正常请求每个图库先按每类 100 个候选读取；只有首轮无法在完整 240 历史下返回 15 张，或固定 5/6/4 配额发生降级时，才扩到每类 256 并完整重选一次。
- 保留 `240 → 210 → 180 → 150 → 120 → 90 → 60 → 30 → 0` 的历史放宽顺序，不以缩短历史换取速度；首轮和扩容中间结果均不得提前落库。
- 每个选择调用只校验并归一化一次候选向量、只建立一次各槽位稳定基础排序；选中图片后增量维护其他候选相对已选集合的最大相似度惩罚，保持现有 MMR 阈值和选择语义。
- 缓存已归一化正向/负向偏好画像、有效反馈数、向量空间摘要和最后显式偏好 sequence；后端重启首次重建，连续换批复用。
- `shown/open/export`、同状态重复反馈和幂等事件回放不得使画像重建；只有某 SHA-256 的最终 `like/dislike` 状态实际变化时，下一批才失效重建。
- 分别记录候选读取（含首轮/扩容）、偏好画像、选择排序、结果回填和总耗时，并记录候选读取次数与画像缓存命中；字段只含有界数值或布尔值，不含路径、viewer/device ID、请求标识、图库标识或偏好内容。
- 当前机器性能门禁：768×1024 纯选择 P95 不超过 1 秒；真实图库冷启动首批不超过 3 秒；热缓存端到端“换一批”P95 不超过 2 秒。

### 技术方案

1. 候选读取先以 `limit_per_pool=100` 执行；使用同一 240 条历史、显式偏好排除和固定请求 seed 完成渐进选择。若结果不是完整 15 张、历史窗口已放宽，或任一活动槽位少于固定配额，则以 256 重新读取、重新加载新增候选的曝光和显式偏好，并只持久化最终选择。
2. 纯选择入口在候选稳定去重后，一次生成 `quality/low_exposure/random` 排序、基础分和合法单位向量。每个历史窗口使用独立的已选状态与最大惩罚映射；每选中一张，只以其单位向量遍历候选并更新最大惩罚。
3. 将偏好向量预处理拆为“构建不可变画像”和“将画像应用到当前候选”两步。推荐单线程 worker 持有一份电脑级缓存；反馈事务返回最终偏好、显式 sequence 和最终状态是否变化，供 worker 精确失效缓存。
4. 后端推荐响应增加安全 `performance` 对象；Windows 本地 bridge 只按字段白名单透传，LAN/Android 响应保持现有契约。后端阶段耗时不含 HTTP 和缩略图预载；端到端实测另从点击换批到缩略图预载、shown 同步及按钮恢复完成为止计时。
5. 微基准固定候选生成、seed、配额、结果摘要、预热和采样次数；正确性测试同时锁定确定性、渐进历史、5/6/4 配额、最低曝光层、random 不个性化、无效/缺失/不兼容向量、共享偏好和旧 `recent` 回放。

### 修改范围

本项仅允许修改以下位置：

- `image_vector_service/recommendations.py`：画像预处理与等价的增量多样性选择。
- `image_vector_service/recommendation_store.py`：在现有事务内返回安全的偏好变化和 sequence；不修改 Schema。
- `image_vector_service/backend_server.py`：100/256 候选读取编排、画像缓存及安全阶段耗时。
- `zvec_host/recommendation_service.py`：仅白名单透传 Windows 本地阶段指标，LAN 调用不透传。
- `tools/benchmark_recommendations.py` 及直接对应的 Python 推荐测试。
- `docs/spec.md`、`docs/technical-changes.md`：同步最终性能行为和实测结果。

不得修改 `state.py` 候选查询语义、推荐数据库四表、240 条历史、viewer 隔离、共享偏好事实规则、模型调用策略、搜索、前端或 Android 业务代码、发布矩阵及其他无关模块；再次强调，不得借性能改动改变 5/6/4 选择结果语义或取消向量多样性。

### 验证项

- 候选读取：正常为 `[100]`；240 历史不足或配额降级时严格为 `[100, 256]`；扩容仍不足时不继续循环，不落中间批次；幂等回放不重新读取。
- 选择等价：固定输入下优化前后 item ID、slot、顺序、history window 和配额一致；基础排序每槽一次、每个候选向量归一化一次，并显著减少相似度计算。
- 降级回归：缺失、零向量、NaN/Inf、维度不兼容、相册/角色限制、SHA 去重和 MMR `.85/.95` 阈值均保持确定性。
- 缓存：冷批读取一次偏好向量；热批、shown/open/export、同状态反馈和幂等回放均复用；最终偏好实际变化后下一批恰好重建一次，重启后的新 manager 首批重建。
- 安全指标：阶段字段只接受已列出的非负数值、计数和布尔值，恶意路径、viewer、图库、请求或偏好字段均不得经过 bridge。
- 性能：同一微基准重跑 300/768 两档并通过 768 P95 门禁；真实图库记录冷启动、至少 20 次热换批 P50/P95、首轮命中/扩容次数及各阶段汇总。
