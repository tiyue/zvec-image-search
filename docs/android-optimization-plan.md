# YaoLens 安卓端优化方案

- 日期：2026-10-08
- 分析基线：`c484dbc`，第三轮 Windows 图库与图片调度优化完成后的源码。
- 状态：用户已确认按文档开发；2026-10-08 A/B 阶段功能完成并通过独立验收，正式性能门禁尚未完成，C 阶段仍需独立确认。详见 [A 阶段验收](android-optimization-round-a.md)、[B 阶段验收](android-optimization-round-b.md)。下文分析证据与历史数字保留原分析时点，不代表新实现结果。
- 主要对象：`android/app` 手机和平板客户端；`android/wear` 本轮不改。
- 目标：更快看到搜索图片、更稳定地连续浏览，让手机与平板界面保持合理密度。

## 1. 推荐结论

建议先做 A 阶段的图片交付与状态修正，再做 B 阶段的移动布局和大图交互。C 阶段的统一图库值得做，但需要补齐 LAN 目录浏览契约，应独立确认后实施。

最有收益的改动不是复制电脑端界面，而是把搜索网格的原图请求改为现有缩略图请求，保留搜索滚动位置，把保存文件的复制移出主线程，并让加载失败在当前页面可见、可重试。推荐页已经具备缩略图、渐进显示和下一批预热，继续复用这些能力。

原方案编写任务仅修改本文件、`docs/spec.md` 和 `AGENTS.md`。后续开发按第 7 节逐项给出精确范围；实际文件与检查记录在阶段验收文档中。不得修改无关部分；数据库、用户图片、Windows 已完成优化及已有 `.qoder/better-harness/` 均不在本轮安卓写入范围。

## 4. A 阶段：图片交付与状态修正

### A1. 搜索网格使用现有缩略图

最小实现是在 `LanApiClient` 增加 `thumbnailUrl(mediaId)`，Repository/ViewModel 提供对应只读接线，搜索 `ResultCard` 使用它。不要改动现有 `mediaUrl()` 的原图语义，不必为了这一项增加数据库字段或改变搜索响应 DTO。

依据：LAN `GET/HEAD /api/v1/media/{media_id}/thumbnail` 已存在；`PreviewLanAdapter.resolve_thumbnail()` 同时查找搜索与推荐 capability，复用共享 `ImageRegistry` 的 640px 缩略图。需要补一个明确覆盖**搜索来源**的契约测试，不能只用推荐测试代替。

具体要求：

1. 网格只请求已显示或有限预取的缩略图，不批量拉取 100 张原图。
2. 详情、保存和分享保留原图路径；原图完整性与续传行为不变。
3. 缩略图失败显示同尺寸占位及重试入口，不自动回退下载整张原图。
4. 第一轮保留 640px 档位、HTTP=10 与生产 render=4。先减少无效字节，再测瓶颈，不直接增加并发或降低画质。
5. 先验证旧电脑端兼容情况：当前分析版本支持该接口；若旧 APK/旧服务端兼容是明确发布要求，再定义受控回退，不能自行加重试和大图回退策略。

### A2. 搜索状态与滚动恢复

- 搜索与推荐各持有独立网格状态；搜索状态提升到不会因查看器切换而退出的页面层，或使用明确的可保存状态容器。
- 普通切 Tab、打开/关闭大图只恢复位置；新搜索明确重置。以当前搜索身份和图片绝对位置/稳定 key 为锚点，密度切换后重定位到同一张图。
- `rememberSaveable`/`SavedStateHandle` 只保存查询草稿、Tab、搜索身份、图片锚点和偏移，不能把整个结果列表或 Bitmap 塞进 Bundle。
- 配置变化尽量恢复正在浏览的会话；进程被回收后，服务端搜索可能过期，应保留草稿并提示重新搜索，不承诺无条件继续旧会话。
- 分页响应提交前检查搜索归属。取消/新搜索/重连后，旧页面、旧错误与旧 loading 完成不能覆盖新状态；推荐已有 generation 保护可借鉴，不能为此重写推荐实现。
- 大图跨页加载依据最新列表边界。现有 `LaunchedEffect(pagerState)` 捕获的初始 `viewerItems` 以及 ViewModel 内的重复触发应在实施前复现；选择一个清晰的触发位置，避免对初始分页边界反复判断。

### A3. 保存原图的主线程与任务状态

- 在 `ZvecRepository.copyOriginalTo()` 内保证同步文件操作 main-safe，保持流式复制，不把完整原图读入内存。
- 增加可验证的取消检查；取消之后不提示“保存成功”，不写成功记录，不提交推荐 `export`。
- 为传输保留固定的媒体目标。弹出系统保存位置选择器后，应按发起时的图片保存，不能依赖稍后可变化的 `currentViewerItem()`。
- 保存成功、失败与分享准备失败都在当前查看器可见，不能只向未挂载的 `SnackbarHost` 发送消息。同步复制失败/取消可能留下目标位置的不完整文件，应明确提示，不自动删除用户已有文件。
- 第一轮采用简单规则：同一时间一个用户传输操作；进行中禁用重复保存/分享，提供取消入口。返回网格时显示该任务的简短进度，不因为查看器关闭就隐藏仍运行的任务。
- 本阶段不扩展后台长期下载服务。若以后要求系统回收后继续下载，再单独评估 WorkManager/前台服务；不要为本次体验修正引入这些机制。

### A4. 上传、空态与失败恢复

| 页面状态 | 建议文案/入口 | 保留内容 |
| --- | --- | --- |
| 初次进入结果页 | “搜索后在这里查看结果” | 搜索入口 |
| 当前查询无匹配 | “没有找到匹配图片”＋“修改搜索” | 查询、图库选择 |
| 首屏搜索失败 | 具体原因＋“重试” | 草稿与查询图 |
| 下一页失败 | 底部“下一页加载失败”＋“重试” | 已加载结果与当前位置 |
| 查询图上传失败 | 图片旁“上传失败”＋“重试 / 移除” | 所选 URI 与文件名，URI 不可用时重新选择 |
| 搜索已取消 | “已取消” | 可再次提交的草稿 |

失败、成功和取消必须是独立状态。不要仅依据 `uploading=false` 判断成功，也不要让全局错误只能在另一个 Tab 看见。上传失败后有文字时是否允许自动降为纯文本搜索，应在交互上明确提示，避免用户以为图片已参与搜索。

## 5. B 阶段：移动布局与大图交互

### B1. 网格密度和全图浏览

- 搜索与推荐共享“紧凑 / 标准 / 大图”布局规则，但保留各自数据和滚动状态。初始建议目标列宽为 112 / 152 / 208dp，间距 8dp、页面边距 8–16dp；这些是待视觉确认的参数，不照搬桌面 px。
- 列数依据可用容器宽度，用现有 Compose 的自适应网格即可。第一版保持规则网格，不引入复杂瀑布流、拖拽或二次分页体系。
- 图片用 `Fit`/等价全图展示；留白使用既有主题底色。卡片高度随密度确定并保持加载前后稳定，避免切换 `Crop` 后产生过高留白。
- 默认卡片至多一行必要文字；尺寸、标签、路径等放详情。推荐不重新加一排喜欢/不喜欢按钮，沿用现有详情反馈。
- 密度选择可本机持久化，与电脑设置独立。改密度不重新执行语义搜索，也不再次调用模型。

### B2. 大图工具栏与渐进显示

建议单击图片显隐工具栏：顶部返回、当前位置；底部保存、分享、更多。文件详情放可滚动 Bottom Sheet，长按菜单保留为快捷入口。工具栏、进度与菜单避让状态栏/导航栏；Back 先关闭菜单，再退出查看器。

第一步复用现有 thumbnail 作为加载占位，然后打开当前原图。Coil 仍承担现有缓存与加载；当前页优先，显式预取最多相邻两张，切源、关闭或 Activity 不可见时取消自己的预取。不要对整个搜索结果或推荐批次预取所有原图。

现有 LAN 的 `preview_url` 仍指向 `/original`，并不存在独立压缩 preview 路由。只有在原图首显实测证明有必要时，才补真正的 LAN preview，复用 `ImageRegistry` 当前 1920px preview。此项属于接口扩展，单独列范围与兼容测试；保存/分享始终获取原始文件字节，不能保存 preview 冒充原图。

当前 LAN 媒体路由拒绝 query，不能把电脑端 `?priority=prefetch` 直接拼到安卓媒体 URL。第一轮先做客户端请求取舍；若后续需要服务端区分预取，则明确新增契约及 adapter 优先级传递。同时处理渲染队列满与媒体不存在的不同响应，避免可重试的忙碌被误报为图片丢失。

缩放时检查实际图片显示边界与旋转后的边界，不只用整个 viewport 计算平移距离；1× 左右滑切图，放大后滑动平移。验证横竖图、长图、旋转、双击复位以及到达结果首尾的行为。客户端取消请求不等于取消服务器已经开始的渲染，不能据此扩大后台队列。

### B3. 搜索与设置

- 保留现有“语义 / 标签”选择，图片和图文联合模式继续由实际输入派生。
- 主输入区增加小尺寸查询图片预览、明确的替换/移除入口；长文件名截断，完整名称在详情可见。

### B4. 视觉规范与页面职责

- 延续现有黑白灰 Material3，复用 `ZvecTheme` light/dark 并跟随系统；没有必要先改品牌配色。
- 历史底部导航仍有默认浅紫选中底色，当前 `ZvecTheme` 也未完整覆盖 secondary container 等语义色。实施时补齐实际使用的容器/内容色并检查深浅主题一致性，避免只修改 `primary` 却遗漏导航、Sheet 和选中状态。
- 使用 8dp 间距体系，必要时 4/12dp；正文保证对比度，标题、按钮和图片不要占据不必要的大块空间。
- 底部导航与主要操作改用有语义的图标/按钮，补充分辨操作的描述。现有 42dp 视觉按钮还需核对 Material3 实际点击区域是否与邻项重叠；留出至少 48dp 的可操作空间，而不是仅把图标做大。
- 大屏先做自适应列数，随后按可用宽度选择 NavigationRail 与可选详情区；手机详情使用 Sheet。不同导航承载同一状态，不产生第二套搜索结果。
- 按需把搜索、结果、推荐、设备与查看器拆到业务页面文件，顶层 `ZvecApp` 负责导航与组合。只搬移本阶段必须改的组件，不先重写全量 ViewModel、不引入通用架构框架。
- 使用生命周期感知的状态收集；若添加 `lifecycle-runtime-compose`，与现行 Lifecycle 2.8.3 系列保持一致，核对现有 BOM/Kotlin 兼容性，不把最新版依赖升级夹带进来。停止 UI 收集并不自动取消 ViewModel 任务，预取和传输分别执行已定义的规则。
- 点击背景、系统返回均能关闭弹出菜单/Sheet，关闭后操作落回可见页面；没有颜色圆点或纯装饰元素。

## 6. C 阶段：只读统一图库与数据层

### C1. 图库能力与导航取舍

在 A/B 阶段先保留“搜索 / 结果 / 推荐 / 设备”四个现有 Tab，优化流程，不先把“结果”改名成尚不存在的“图库”。

若确认需要安卓目录浏览，推荐最终导航为“图库 / 搜索 / 推荐 / 我的”；搜索结果作为搜索流程内的二级页面。这里“我的”承载连接与已保存文件。这个导航变化应先确认安卓原型，再实施；不能机械继承电脑端六项菜单。

图库默认只读：图库选择 → 文件夹 → 缩略图 → 大图。手机目录用 Sheet/二级列表，平板可侧栏与网格并排。浏览、搜索和推荐复用媒体显示与查看器；数据来源、分页及滚动锚点各自独立。第一版不新增标签写入、删除图库、索引管理、ARW 选片或图片编辑。

LAN 当前没有目录路由。实施前定义库/根目录/文件夹标识、分页/排序、总数、媒体绑定与失效行为，复用 `LibraryBrowser.list_folders()`、`folder_images()` 和 `IndexStateReader`。接口文档先确定再接 Android；不得复制一套目录扫描器，也不能直接把桌面 facade 返回字段原样暴露成 LAN 契约。

### C2. 数据库与本地持久化

| 数据 | 当前方式 | 建议 |
| --- | --- | --- |
| 图片索引与搜索排序 | Windows 后端统一维护 | 安卓只消费结果，不复制向量库或模型到手机 |
| 图库目录 | `LibraryBrowser` 复用现有 SQLite 只读查询 | 先复用现有分页；只有慢查询复现后才检查执行计划与必要索引 |
| 当前搜索结果 | PersistentList，网络每页 100 项 | 第一轮保留结构共享；大 `top_k` 的内存问题实测后再评估 Paging 3/页窗口 |
| 查询草稿、Tab、图片锚点 | 内存/部分 `rememberSaveable` | 只持久化恢复所需的小状态；明确过期搜索的重新提交流程 |
| 已保存记录 | SharedPreferences JSON，最多 200 项 | 规模足够小，先保留；打不开时显示原因，允许移除失效记录而不删除用户文件 |
| 本地原图缓存 | Coil 磁盘缓存与独立 `shared-media` | 先测重复 HTTP、文件占用和命中率，再决定原始字节复用与有界淘汰 |

目前没有依据要求立刻引入 Room。只有要做可查询的本地下载历史、离线元数据、批量任务或显著更多记录时，才评估数据库迁移，并定义版本、回滚和验证。

缓存复用必须使用可确认的完整原始响应字节；不能把缩略图、解码后的 Bitmap 或只完成一部分的文件当作原图。媒体 ID 可能随搜索会话变化，缓存 key 的跨会话复用必须有内容/版本依据，不能单凭文件名合并。淘汰只限应用自己的缓存，不清理用户保存的文件，也不为了首轮优化扩大缓存容量。

## 8. 验收标准

### 8.1 必须通过的功能项

1. 同一搜索在文本、标签、图片、图文联合模式下结果顺序、总数与原图内容保持一致；图片上传失败不能显示成功。结果数量非法输入、零结果、取消、首屏失败、下一页失败均有可见状态。
2. 搜索列表 HTTP 只取缩略图；点击查看、保存、分享获取对应原图。保存文件哈希与来源一致，206/If-Range/416 现有行为保持，取消不计成功。
3. 滚到后续页面，打开任意图、关闭大图、切 Tab、旋转后回到同一图片及合理偏移；新搜索只重置自己的位置。后台翻页不切走“设备/推荐”等主动选中的页面。
4. A→B 新搜索、取消再搜索、切库、断开/重连后，旧成功/失败/取消响应均不能污染当前查询。大图在第 99/100 项跨页时不重复跳页、漏图或陷入连续请求。
5. 大图菜单可由可见入口和长按打开；背景点击/Back 可关闭；1× 翻图、放大平移、双击复位、旋转和首尾边界正确。原图失败可重试并可退出。
6. 保存任务绑定发起时的图片；重复操作不会静默取消前一次。关闭查看器后任务状态仍可见，成功只记录一次，取消/失败不发推荐 `export`。
7. 保留推荐 15 张、固定前 4 张成功后显示、shown/event_id 幂等、至多一批预热、隐藏取消预热与确认后的偏好反馈；不把普通搜索曝光写入推荐历史。

### 8.2 性能测量口径

所有数字须标明客户端版本、设备、网络、图片样本、缓存状态和是否包含 Compose 首次绘制。分别测服务端搜索、首张缩略图、首屏可见图片、大图首显、保存复制、滚动掉帧与两端峰值内存；下载完成不能代替界面已画出。

历史 TC-007 记录：API 34 模拟器、HTTP=10/render=4 的推荐前 4 张 P95 为 2427.430ms、全 15 张为 2601.598ms；旧目标分别是 1.5s 和 2.2s，未通过。预热状态提交 0.087ms 不包含 Compose 绘制，不能当作首屏渲染时间。这些是历史环境结果，不是当前手机基线，也不能拿推荐耗时直接代表搜索。

| 指标 | 首轮验收要求 |
| --- | --- |
| 搜索列表字节 | 同一组普通图片、同一结果顺序，缓存受控时比旧原图列表至少减少 80%；记录实际字节，不用解码尺寸推算 |
| 搜索首屏 | 先在同一真机建立前值，再以至少降低 30% 的首屏 P95 为目标；达不到时拆分网络/渲染/解码原因，不声称已达标 |
| 返回与状态 | 位置恢复不重新 createSearch、不重传查询图片；缓存命中/过期情况分别记录 |
| 文件复制 | 用可控阻塞复制与主线程心跳确认不阻塞 UI；真机保存大文件无 ANR，哈希一致 |
| 公平性 | 同时使用 Windows 时，轻量 API P95 相对同环境基线不回退超过 10%；无无界请求积压 |
| 资源 | 保留 HTTP=10/render=4；记录峰值与取消后的残留；不以提高并发或隐藏错误换速度 |

流量目标用缩略图占比明显的代表性普通大图样本验证，超小原文件样本单列，不宣称每个文件都减少 80%。推荐预热、全热缓存、首次生成和原图首次解码各自报告，不能混为一个指标。

## 9. 取舍与回退

- **先用缩略图**：减少网络和解码成本，但尚不能保证首次缩略图生成很快；原图行为保留，客户端接线可独立回退。
- **先保留四个 Tab**：A/B 更容易验证原有流程；C 再统一图库会增加一次导航调整，需要原型确认。
- **先规则网格**：便于滚动锚点、分页、读屏与跨设备验收；是否瀑布流另看真实素材和用户偏好，不照搬桌面实现。
- **先不加 Room/Paging 3**：现有记录有界、结果结构共享，改库/分页框架的收益尚未证实；大结果集实测后再决定。
- **分阶段提交**：A、B、接口扩展与 C 各自独立。每阶段只恢复自身文件，不回滚真实图片、索引或 Windows 已完成的优化；缓存变更需要单独记录格式与回退方式。
